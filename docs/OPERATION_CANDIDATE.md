# Operation and reconnect candidate

This source contains an offline review candidate for separate recording settings and erase operations. The development GUI now connects these functions through `app/camera.py`; button flows have been tested with simulated serial only. The activation candidate accepts only fully verified operation/reconnect bindings with the current policy revision and an explicit false candidate-block flag. Old blocked evidence is rejected. Independent activation-diff review is required before hardware use. The existing read-only and erase-then-Detailed paths remain separate.

A recording-settings plan fixes one NP byte (01, 02, 03, 09, 0A or 0B). An erase-records plan fixes empty EP. Neither can send the other's command. The workflow saves and re-reads a backup, records explicit confirmation, re-reads the full camera state, attempts the single write, and checks the resulting state. Writes do not retry after 79, short transfer, missing response or any other failure. Unknown MQ bits block NP. Every actual settings write requires OQ=0, one-byte LQ and zero frames, plus a separate operator observation of counter E followed by another full state read. These are simulated tests, not validation of all six values on hardware.

Reconnection uses a separate registration that preserves the entire original first-inspection evidence set. Each reconnect requires a fresh observation matching the same exact port, USB identity and full enumeration/topology. Changes require first inspection again. Historical evidence is not timestamp-refreshed and no new camera-disconnected assertion is created. A cable match does not establish a camera response, electrical safety or firmware authenticity. Hashes provide evidence continuity, not user authentication.

The old orchestrator's read-only capture acceptance deliberately rejects these new write scopes. No automatic end-to-end acceptance of a write session is claimed; raw capture and operation results still require operation-specific review. The new scopes have a GUI entry point, but no separate live CLI entry point. The policy amendment is approved. Independent review of this enabling change, GUI integration review and hardware checks remain before end-user operation.
